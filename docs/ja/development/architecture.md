# 🧩 プレイヤーの構成

SpriteStudio Player for Godot を開発する人と、自分のプロジェクトのために改造する人に向けたページです。部品をその役割で説明します。ビルド、変更した版をプロジェクトで使う方法、Godot での確かめ方は[ビルドガイド](build.md)に、制約とテストスイートは [CONTRIBUTING](https://github.com/cri-middleware/SSPlayerForGodot/blob/HEAD/CONTRIBUTING.md) にあります。

SpriteStudio の Player に共通すること（再生・モーションブレンド・サウンドキー・パーツトラッキングの振る舞い）は、SDK の [Player Porting Guide](https://github.com/cri-middleware/SpriteStudio-SDK/blob/HEAD/libs/ssruntime/docs/README.md) に一度だけ書いてあります。

## 層

プレイヤーはすべて `ss_player/` の下の C++ で、同じ 1 つのソースから 2 通りにビルドします。`godot-cpp` の上の **GDExtension** と、エンジンに組み込む **カスタムモジュール** です。`#ifdef SPRITESTUDIO_GODOT_EXTENSION` のブロックが持つのは、2 つで異なる include と型の変換だけです。

**再生。** `SpriteStudioPlayer2D` がノードで、プロパティ・メソッド・シグナルを持ちます。その下に、ノードを持たない再生コアがあります。コアは C API で `libssruntime` を動かし、各フレームの描画バッチをたどり、`RenderingServer` で 1 つのルートのキャンバスアイテムに描きます。Instance パーツごとに子のコアを 1 つ持ち、マスク・エフェクト・パーツごとのメッシュもそこにあります。キャンバスアイテムのシェーダーは、マテリアルを作るときに GLSL の部品から組み立てます。音は `SpriteStudioAudioBackend` が引き継がない限りプレイヤーが鳴らし、`SpriteStudioPartAttachment2D` はパーツに追従する利用者のノードです。変換したファイルは `SSABResource` と `SSQBResource` が読み込み、`.ssab` の解析結果は、それに結び付いたすべてのプレイヤーで共有します。ランタイムのライブラリは `ss_player/runtime/` に、`download-sdk` か `build-runtime` が置きます。

**エディタ**（エディタのビルドにだけ入ります）: **SS Importer** ドック（ドロップ・最近使ったファイル・Reconvert）、ファイルシステムドックの右クリックメニュー、`SSABResource` のインスペクタ、プレイヤーを選んだときに出る再生パネル、`.ssab` を 2D ビューポートにドロップしてプレイヤーを作る機能です。インポーターは `libssconverter` で `.sspj` を変換し、出力フォルダごとの変換元を `res://.ssplayer_sources.cfg` に記録します。

**周辺:** `misc/spritestudio.gdextension` は拡張のマニフェストで、どの `addons/spritestudio/` にもコピーされます。`test_gdextension/` はヘッドレスのスイートで、サンプルではありません。`examples/` はサンプルで、`dev_gdextension` と `dev_module` は開発用の作業プロジェクトです。`godot/` と `godot-cpp/` はサブモジュールではなく、repo の横に clone します。

## この作りになっている理由

ここに挙げる理由はどれも複数のファイルにまたがります。詳細は、関わるコードのコメントにあります。

**再生コアはノードを持ちません。** コアはルートのキャンバスアイテムを持って `RenderingServer` で描き、`SpriteStudioPlayer2D` がそれを包みます。100 パーツのアニメもシーンツリーでは 1 つのノードで、コアはツリーに依存しません。要るのは親のキャンバスアイテムと、イベントの送り先だけです。`SpriteStudioPartAttachment2D` があるのは、パーツへの追従が、利用者が自分のノードを必要とする唯一の場面だからです。

**マスクはステンシルではなくカバレッジのビットマップです。** Godot のキャンバスにはプラグインが使えるステンシルバッファが無いため、毎フレーム、マスクの書き手をオフスクリーンのビットマップに 1 つ 1 ビットで描き、マスクされる各パーツのシェーダーがそれを読み戻します。1 枚のビットマップがインスタンスツリー全体を受け持ち、その持ち主は最上位のプレイヤーです。ビットは RGB に詰め、1 タイルに 24、最大 4 タイルなので、1 フレームに書き手は 96 までです。それを超えた書き手は警告を 1 回出して捨て、それ以上が要るツリーは受け入れるのではなく組み直してもらいます。ビットマップはプロセス全体で 1 つのプールから借りるので、ビデオメモリは、これまでにマスクしたプレイヤーの数ではなく、同時にマスクしているプレイヤーの最大数で決まります。

**音はプレイヤーが鳴らし、そのボイスはプールします。** ランタイムが伝えるのは、サウンドキーを通過したことだけです。このプレイヤーはそれを自分で鳴らします。Unity・Web・Ren'Py のプレイヤーもそれぞれのエンジンで同じことをし、Flutter・React Native・wgpu のプレイヤーは通知をアプリに渡します。音は 1 つごとに新しい `AudioStreamPlayer` で、必要になったときにプレイヤーの内部の子として作ります。シーンツリーには出ず、保存もされません。指定の回数を鳴らし終えたらプールに戻すので、忙しいアニメでもノードを作っては捨てることになりません。アニメを一時停止しても、音は最後まで鳴ります。それがすべての Player が守る規則である理由は、SDK のポーティングガイドにあります。`SpriteStudioAudioBackend` を割り当てると、組み込みの再生は完全に止まります。

**名前では使えるのに、どこにも保存されないプロパティがあります。** `frame_rate`・`playback_direction`・`playback_style` は `_set` / `_get` で扱い、プロパティの一覧からは外しています。スクリプトからは設定できますが、インスペクタにも保存したシーンにも載りません。スクリプトで設定した値は、シーンを読み直すと消えます。

**出力フォルダごとの変換元は、プロジェクトに記録します。** `res://.ssplayer_sources.cfg` が出力フォルダごとにその `.sspj` を記録していて、Reconvert・ファイルシステムのメニュー・`deploy-examples` が出どころを尋ねずにパックを作り直せるのはこのためです。ドックの最近使ったファイルは別の置き場で、コミットしない `.godot/` の下にあるエディタのプロジェクトメタデータなので、マシンごとのものです。

**モジュール版を守るのは、コンパイルが通ることだけです。** スイートが動かすのは GDExtension で、モジュール版を試すにはエンジンをビルドする必要があります。2 つのビルドが再生のロジックを 1 つ共有し、`#ifdef` のブロックが include と変換しか持たないのはこのためです（`run-tests.sh` のヘッダーにも同じことがあります）。
